Building a system that supports a single user, then scale it up to serve millions of users.
Starting, everything begins from a single server.
![[Pasted image 20261008133131.png]]
With the growth of the userbase, one server isn't enough, we need multiple servers: one for web/mobile traffic and the other for the database
![[Pasted image 20261008133145.png]]
Why do we separate them?
- To allow for them to be scaled independently.

Which DBs to use?
- Relational: tables -> columns and rows (can perform joins using SQL)
- Non Relational -> key-value store, graph store, column store, document store (joins are generally not supported here)

Scaling: Vertical vs Horizonal
Vertical: scale-up :-
- add more CPU/RAM to the existing server
- it's impossible to add unlimited CPU and memory to single server
- scaling doesn't handle failover/redundancy if one server goes down, app goes down completely
Horizontal: scale-out :-
- scale by adding more servers to your pool of resources
- desirable for large scale applications

From the single server architecture, users cannot access the website if webserver is offline
Also, if many users access the webserver simultaneously & the server's load limit is reached, users would experience slow response/fail to connect to server.
Hence, a load balancer is best technique here

## Load balancer
This distributes incoming traffic to web servers that are defined in a load-balancer set
![[Pasted image 20261008134541.png]]
For better security, the web servers are unreachable directly by the client anymore, and private IPs are used hence.
This works well for servers, and can scale to have more servers, let's look at dbs now to handle failover & redundancy.

## Database replication
Used in DB management systems, with master/slave relationship btw the original (master) and copies (slave)
- Master generally supports only write operations. 
- Slave dbs get copies of data from the master database and supports read operations
- Commands like "insert", "delete", "update" must be sent to the master db
*most app support higher ratio of reads to writes*, thus number of slave is usually larger than number of master dbs
![[Pasted image 20261008135932.png]]

Now let's talk about improving *load/response* time. Done using a cache layer & shifting static content (js/css/img/video) to a CDN (content delivery network)

## Cache
A temp storage area for storing results of expensive responses/frequently accessed data in memory so they can be served more quickly.

## Cache tier
A temporary data store layer, faster than a db.
A single cache server represents a potential single point of failure (SPOF). Multiple cache servers across diff data centers are recommended hence.

## Stateless web tier (horizontal scaling)
The state has to be moved out of the web server (user session data). Store session data in the persistent storage such as the db. So that each web service in the cluster can access state data from dbs. This is called stateless web tier.

### Stateful architecture
A stateful server remembers client data from one request to the next. Stateless keeps no state information

Message queue:
this is a durable component, stored in memory, supporting async communication.
- Input services (producer/publisher) create message ––> publish them to the message queue
- Other services (consumers/subscribers) connect to the queue & perform actions defined by the messages

### Horizontal db scaling (sharding)
Adding more servers for the dbs. Separates large dbs into smaller, more easily managed parts called shards. Each shard shares same schema, though the actual data on each shard is unique to the shard
