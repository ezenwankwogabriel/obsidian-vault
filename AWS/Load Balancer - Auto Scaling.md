A load balancer doesn't auto create more servers. You can combine it with an Auto Scaling Group to add and remove EC2 instances based on demand

Types of Load Balancers
- Application LB (ALB)
	- Understands HTTP(S) rerquests and can route traffic based on URL path, hostname or HTTP headers
- Network LB (NLB)
	- Handles TCP, UDP, & TLS traffic at the transport layer, with very high performance & low latency
	- example: a high throughput app requiring millions of connections / service using TCP
	- cue: ultra low latency, static IP add, TCP/UDP traffic
- Gateway LB (GLB)
	- Distributes traffic to virtual network applicnaces, such as firewalls and intrusion detection systems
	- example: send network traffic through multiple security appliances for security
	- cue: third-party virtual app, firewall, transparent traffic inspection
- Classic LB (CLB)
	- the older generation of AWS lb. supports basic layer 4 & 7 load balancing
	- cue: legacy app

Application LB is Layer 7 for app routing

### Network Load Balancer (v2): gives you fixed ip addresses
	This is a layer 4 load balancer allowing you Forward TCP & UDP traffic to your instances
	
	It has only one static IP per AZ, and supports assigning Elastic IP to each AZ (for whitelisting specific IP)
	When asked about accessing the resource using a pool of IP, think of the NLP as an option

	You create target groups and the load balancer redirects to them
	Can route to 
		EC2 instances
		Private IP Address
		Application Load Balancers

	Health check supports TCP, HTTP, and HTTPS Protocols

### Gateway Load Balancer
	To deploy, scale, and manage a fleet of 3rd party network virtual apps
	If you'd want all traffic to go through a Firewall, Initrusion Detection, ...
	This would be similar to what cloudflare does, inspects traffic before it is sent to actual applications/ec2 instances

	This operates in the Layer 3 (network layer) IP packets
	It combines:
		Transparent Network Gateway: single entry/exit for all traffic
		Load Balancer: distribute traffic to your virtual apps
	Uses Geneve protocol on port 6081

	Target groups can be `Ec2 instances, Private IP Addresses`

### Sticky Sessions (Session Affinity)
To maintain same redirect where one request always go to same instance as opposed to balancing it among the instances
This works for CLB, ALB, and NLB
Uses a cookie for stickiness, and has an expiration date you control

Type:
	Application-based cookie:
		Custom Cookie:
			Generated by the target
			Cookie names must be specified individually for each target group
			Dont use AWSALB, AWSALBApp, or AWSALBTG (reserved for use by ELB)
		Application Cookie:
			Generated by the load balancer
			Cookie name is AWSALBAPP
	Duration-based cookie
		Cookie generated by load balancer
		cookie name is AWSALB for ALB, AWSELB for CLB

### Cross-Zone Load Balancing
Given an availability zone AZ 1 (2 ec2 instances) and AZ 2 (8 ec2 instances). each AZ handled by an LB. thats 10 EC2 instance in total
On 100 requests, with cross-zone LB, the EC2 instances all get 10 requests each, 20 on the first LB and 80 on the second LB
Without cross-zone, each LB gets equal requests. AZ 1 gets 50 (25 each for the 2 EC2 instance) and AZ2 gets 50 (shared among the 8 EC2 instance)


*By default, Cross-Zone LB is enabled for ALB. No charges for inter AZ data*
*for NLB and GLB, Cross-Zone is disabled by default. If you choose to enable, you'd be charged*
*For CLB, it's disabled by default, and wouldn't be charged if enabled*


## AutoScaling Group
Application load changes in real-life, and in Cloud, you can create and get rid of servers quickly
The goal is to:
	Scale out (add EC2 instance) to match increased load
	Scale in (remove EC2 instance) to match decreased load
	Ensure we have a min/max no of EC2 running
	Auto register new instances to a load balancer
	Recreate an EC2 instance in case a previous one is terminated
ASGs are free (you pay only for the underlying EC2 instances)

You set a min capacity (2), then a desired capacity (4), and a maximum capacity (6)

Users > ELB > ASG > EC2 Instances

## Scaling Policies
	Dynamic Scaling
		Target Tracking Scaling
			Define a target value: ex: average ASG CPU to stay at around 40%
		Simple/Step Scaling
			When cloudwatch alarm is triggered, add or remove instances
	Scheduled Scaling
		Anticpate a scaling based on known usage pattern (new launch, ...)
		Predictive scaling: forcast load and schedule scaling actions ahead

### Good metrics to scale on
- CPU Utilization
- RequestCountPerTarget: make no of request per EC2 instance stable
- Average network in/out (app is network bound). if a threshold is reached, scale
- any custom metrics (ex: from cloudwatch)

Cooling Down

during this period ASG will not launch or terminate additional instances(to allow metic cooldown
