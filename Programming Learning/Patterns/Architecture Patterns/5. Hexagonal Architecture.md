Also called:

> **Ports and Adapters**

This one becomes easier when you visualize it.

```
                 REST API
                    │
                 Adapter
                    │
                    ↓
             ┌─────────────┐
             │             │
             │   DOMAIN    │
             │             │
             │ APPLICATION │
             │             │
             └─────────────┘
                ↑       ↑
                │       │
             Adapter  Adapter
                │       │
             Postgres  RabbitMQ
```

The core defines **ports**:

```
interface UserRepository {
    find(id: string): Promise<User>;
}
```

An adapter implements it:

```
class PostgresUserRepository implements UserRepository {
}
```

Another adapter could be:

```
class MongoUserRepository implements UserRepository {
}
```

The application doesn't care.

This is why it's called:

> **Ports and Adapters**

The application is the center.

External things plug into it.

#### Example
###### the architecture
```
                    HTTP
                     │
                     ▼
              ┌─────────────┐
              │ HTTP Adapter│
              └──────┬──────┘
                     │
                     ▼
          ┌─────────────────────┐
          │     APPLICATION     │
          │                     │
          │   CreateOrder()     │
          └──────────┬──────────┘
                     │
                     │ Port
                     ▼
             OrderRepository
                     │
                     ▼
              ┌─────────────┐
              │ DB Adapter  │
              └──────┬──────┘
                     │
                     ▼
                PostgreSQL
```

###### project structure
A simple version:
```
order-service/
│
├── domain/
│   └── order.go
│
├── application/
│   └── create_order.go
│
├── ports/
│   └── order_repository.go
│
├── adapters/
│   ├── http/
│   │   └── handler.go
│   │
│   └── postgres/
│       └── repository.go
│
└── main.go
```

Don't get too attached to this exact folder structure. The important thing is the **dependency relationships**.

######  Domain
Start with the business object.

```
// domain/order.go

package domain

type Order struct {
	ID     string
	Amount int
}
```

Now let's say there's a business rule:

```
func NewOrder(id string, amount int) (*Order, error) {
	if amount <= 0 {
		return nil, errors.New("amount must be greater than zero")
	}

	return &Order{
		ID:     id,
		Amount: amount,
	}, nil
}
```

Notice:

```
domain
   ↓
doesn't know about HTTP
doesn't know about PostgreSQL
doesn't know about RabbitMQ
doesn't know about Gin
doesn't know about Echo
```

That's your **core business**.

###### Define a port
Now our application needs to save an order.
We could directly use PostgreSQL:

```
db.Exec(...)
```

But then the application becomes coupled to the database.

Instead:
```
// ports/order_repository.go

package ports

import "order-service/domain"

type OrderRepository interface {
	Save(order *domain.Order) error
}
```

This is a **port**.

It's essentially saying:

> "I need something that can save an Order."

It doesn't say how.

###### Application
Now create the use case.
```
// application/create_order.go

package application

import (
	"order-service/domain"
	"order-service/ports"
)

type CreateOrder struct {
	repository ports.OrderRepository
}

func NewCreateOrder(
	repository ports.OrderRepository,
) *CreateOrder {
	return &CreateOrder{
		repository: repository,
	}
}

func (uc *CreateOrder) Execute(
	id string,
	amount int,
) error {

	order, err := domain.NewOrder(id, amount)
	if err != nil {
		return err
	}

	return uc.repository.Save(order)
}
```

This is the heart of the example.

Look at what it knows:

```
CreateOrder
     │
     ├── knows Domain
     │
     └── knows OrderRepository interface
```

It does **not** know:

```
PostgreSQL
SQL
HTTP
RabbitMQ
```

###### Now create the PostgreSQL adapter

Here's where the actual technology enters.

```
// adapters/postgres/repository.go

package postgres

import (
	"database/sql"
	"order-service/domain"
)

type OrderRepository struct {
	db *sql.DB
}

func NewOrderRepository(db *sql.DB) *OrderRepository {
	return &OrderRepository{
		db: db,
	}
}

func (r *OrderRepository) Save(
	order *domain.Order,
) error {

	_, err := r.db.Exec(
		"INSERT INTO orders (id, amount) VALUES ($1, $2)",
		order.ID,
		order.Amount,
	)

	return err
}
```

This is an **adapter**.

It adapts:

```
Application's requirement
        ↓
OrderRepository.Save()
        ↓
PostgreSQL
```

---

###### Here's the really important part

Notice that PostgreSQL implements the interface:

```
type OrderRepository interface {
	Save(order *domain.Order) error
}
```

And:

```
type OrderRepository struct {
	db *sql.DB
}

func (r *OrderRepository) Save(...) error {
	// PostgreSQL
}
```

Go doesn't require you to explicitly say:

```
implements OrderRepository
```

It automatically satisfies the interface because it has the required method.

So:

```
             PORT
               │
               │
      OrderRepository
               ▲
               │
          implements
               │
               │
      PostgreSQL Adapter
```

That's one of the beautiful parts of Go's interfaces.

# 8. HTTP adapter

Now we need something that receives HTTP.

For simplicity, using the standard library:

```
// adapters/http/handler.go

package httpadapter

import (
	"net/http"
	"order-service/application"
)

type Handler struct {
	createOrder *application.CreateOrder
}

func NewHandler(
	createOrder *application.CreateOrder,
) *Handler {
	return &Handler{
		createOrder: createOrder,
	}
}

func (h *Handler) CreateOrder(
	w http.ResponseWriter,
	r *http.Request,
) {
	err := h.createOrder.Execute(
		"order-123",
		100,
	)

	if err != nil {
		http.Error(w, err.Error(), 400)
		return
	}

	w.WriteHeader(http.StatusCreated)
}
```

This is another adapter.

It converts:

```
HTTP request
     ↓
CreateOrder.Execute()
```

The application doesn't know that HTTP exists.

# 9. Now the interesting part: main.go

This is where **Dependency Injection** happens.

```
func main() {

	db := connectToPostgres()

	// Adapter
	orderRepository := postgres.NewOrderRepository(db)

	// Application
	createOrder := application.NewCreateOrder(
		orderRepository,
	)

	// HTTP adapter
	handler := httpadapter.NewHandler(
		createOrder,
	)

	http.HandleFunc(
		"/orders",
		handler.CreateOrder,
	)

	http.ListenAndServe(":8080", nil)
}
```

Look at what's happening:

```
             main.go
                │
                │ creates
                ▼
      PostgreSQL Adapter
                │
                │ injected into
                ▼
        CreateOrder
                │
                │ injected into
                ▼
          HTTP Handler
```

This is **Dependency Injection**.

We're constructing the dependency graph in `main`.

# 10. The entire flow

When you call:

```
POST /orders
```

you get:

```
HTTP Request
     │
     ▼
HTTP Adapter
     │
     ▼
CreateOrder.Execute()
     │
     ▼
Domain.NewOrder()
     │
     ▼
OrderRepository.Save()
     │
     ▼
Postgres Adapter
     │
     ▼
PostgreSQL
```

But notice something subtle.

The application sees:

```
repository.Save(order)
```

It doesn't see:

```
postgres.Exec(...)
```

That's the whole point.

# 11. Now swap PostgreSQL for MongoDB

Suppose tomorrow you decide to use MongoDB.

You don't need to change:

```
CreateOrder
```

You just create another adapter:

```
type MongoOrderRepository struct {
	db *mongo.Database
}

func (r *MongoOrderRepository) Save(
	order *domain.Order,
) error {

	// MongoDB implementation

	return nil
}
```

It satisfies:

```
ports.OrderRepository
```

Then:

```
orderRepository := postgres.NewOrderRepository(db)
```

becomes:

```
orderRepository := mongo.NewOrderRepository(db)
```

And the application remains unchanged.

That's the power you're trying to get from Hexagonal Architecture.

# 12. You can do the same thing with payment

Imagine the application needs to charge a customer.

Define another port:

```
type PaymentGateway interface {
	Charge(amount int) error
}
```

Stripe becomes an adapter:

```
type StripePaymentGateway struct {
	client *stripe.Client
}

func (s *StripePaymentGateway) Charge(amount int) error {
	// Stripe API
	return nil
}
```

But tomorrow you could use:

```
StripePaymentGateway
        OR
PaystackPaymentGateway
        OR
FlutterwavePaymentGateway
```

The application only knows:

```
PaymentGateway
```

So now your architecture looks like:

```
                         HTTP
                          │
                       Adapter
                          │
                          ▼
                ┌─────────────────┐
                │                 │
                │   APPLICATION   │
                │                 │
                │  CreateOrder    │
                │                 │
                └─────┬─────┬─────┘
                      │     │
                   Port    Port
                      │     │
                      ▼     ▼
                  Repository  PaymentGateway
                      │          │
                    Adapter    Adapter
                      │          │
                      ▼          ▼
                  Postgres     Stripe
```

**That's Hexagonal Architecture in practice.**

# 13. Why call them "ports"?

Think about your laptop.

It has:

```
USB port
HDMI port
Ethernet port
```

The laptop doesn't care exactly which USB device you plug in.

The **port defines the contract**.

Same idea:

```
Application
     │
     │
     ▼
PaymentGateway   ← port
     ▲
     │
     │
StripeAdapter    ← adapter
```

The application says:

> "Give me something that satisfies this port."

The adapter says:

> "I know how to connect this port to Stripe."

# 14. And this explains Onion vs Hexagonal

Now you can see why they look so similar.

The same code could reasonably be described as **Onion Architecture**:

```
Infrastructure
     ↓
Application
     ↓
Domain
```

Or **Hexagonal Architecture**:

```
             HTTP Adapter
                   ↓
            ┌────────────┐
            │ Application│
            │   Domain   │
            └────────────┘
              ↑       ↑
              │       │
           DB Adapter  │
                      │
                 Payment Adapter
```

Or **Clean Architecture**:

```
Infrastructure
      ↓
Interface Adapters
      ↓
Application
      ↓
Domain
```

They're emphasizing slightly different things, but **the underlying code can be almost identical**.

---

## The one thing I'd really want you to take away

Don't memorize:

> "Onion has these circles, Hexagonal has ports, Clean has these four rings..."

Instead, look at the dependency:

```
                EXTERNAL WORLD
                      │
            ┌─────────┴─────────┐
            ↓                   ↓
        HTTP Adapter        DB Adapter
            │                   ↑
            ↓                   │
        ┌──────────────────────────┐
        │       APPLICATION        │
        │                          │
        │      DOMAIN / RULES      │
        │                          │
        └──────────────────────────┘
```

**The core should not depend on the external technology.**

That's the fundamental idea.

And **interfaces + dependency injection are mechanisms that help you achieve it**. They aren't what makes something Hexagonal by themselves.

Given your Go learning, the next really useful step would be to see **the same small application implemented three ways: normal layered → hexagonal → vertical slice**, because then you'll see exactly what changes and what _doesn't_.
